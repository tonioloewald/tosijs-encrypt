## Fix before the tag

### M1. decrypt() rejects 16- and 24-byte keys that 1.0.0 accepted, so stored data becomes unreadable after a semver-minor update. Verified (correctness + blast-radius, both confirmed by repro). Owner decision on which fix.

- **Where:** `src/encrypt.ts:63-76` (`keyBytes()`), called from `decrypt` at about line 150. Also `CHANGELOG.md:32`.
- **What happens:** 1.0.0 passed the raw key bytes straight to `importKey`, which treats 16- and 24-byte keys as AES-128 and AES-192. A user who brought their own short key has ciphertexts stored under it. A `^1.0.0` range installs 1.1.0 automatically. After that, `decrypt(stored, key)` throws `Invalid key: expected 32 bytes (AES-256), got 16.` 1.1.0 gives no way to read this data. The CHANGELOG line "Ciphertexts written by 1.0.0 still decrypt" is false for these users.
  - Repro script: `/private/tmp/claude-501/-Users-tonioloewald-tosijs-encrypt/92e52725-2771-42f4-9e02-8eac1a63669c/scratchpad/repro.ts`
- **What limits the impact:** only users who supplied their own keys are affected. `generateKey()` always produced 32 bytes, and the 1.0.0 docs already said "AES-256". The data can be recovered by pinning 1.0.0 or by decrypting with raw WebCrypto, because the wire format is unchanged.
- **Fix (pick one):**
  - **(a) Recommended.** Keep rejecting short keys in `encrypt()` so no new weak ciphertext is written. Let `decrypt()` accept 16, 24 and 32 bytes, optionally with a one-time `console.warn` deprecation. Make decrypt strict in 2.0.0. In the CHANGELOG, say that short keys are rejected for encryption and still read for decryption, and give the re-encrypt step.
  - **(b)** Ship as **2.0.0** with a **Breaking** note and a migration step: pin 1.0.0, decrypt, then re-encrypt under a `generateKey()` key.
- **Check that clears it:**
  - For (a): add a test that decrypts a fixed 1.0.0-format ciphertext made with a 16-byte key (and one with a 24-byte key) and gets the plaintext back, while `encrypt` with the same key still throws `Invalid key`. Confirm the test fails when the decrypt relaxation is reverted.
  - For (b): package.json is at 2.0.0, the CHANGELOG has a Breaking/migration section, and line 32 is qualified.
- **Also closes:** the CHANGELOG-sentence minor (docs + security) listed under TODO.md below, and most of the README-migration minor.

**Findings with security relevance:**
- **M1 (major).** Short keys rejected in decrypt, causing a data-access break in a minor release. Verified by adversarial repro (correctness and blast-radius lenses, plus a skeptic pass). Disposition: **fix before the tag** (legacy decrypt path, or 2.0.0). It cannot be exploited by an attacker because key length is the caller's choice, so no GHSA or npm deprecate is needed. Residual risk if it shipped unfixed: users with self-supplied AES-128/192 keys could not read stored data until they pinned 1.0.0.
- **CHANGELOG migration note (minor).** Verified by a skeptic pass, severity adjusted from major to minor. Disposition: fixed together with M1. Residual risk until fixed: affected users have no documented recovery path.
- **Security claims not enforced by tests (minor, unverified).** Covers non-extractable keys and uniform error messages. Disposition: filed to TODO.md, deferred as test hardening. Residual risk: a future refactor could reintroduce extractable keys or an error oracle without any test failing.
